# P2 — offline engine (Framework track) — TRIMMED

**Status after design review: TRIM SEVERELY.** The original P2 ("a ~300-LOC
in-process Go agent `AgentRunner` with a local `mlx-go-lm` tool-calling backend")
is **cut**. The existing `mlx-go-sia` `ExecRunner` already does the job, and a
weak local model driving an in-process tool loop is a day-eating timeline risk
with zero novel demo value. This spec now describes the *minimal* thing that
still earns the **"fully offline self-improvement"** claim.

**One-liner:** Earn the offline claim by pointing the existing `ExecRunner` at a
thin wrapper around the already-built `mlx-lm-generate` CLI — no new Go agent
loop, no new model SDK dependency.

## Why the trim is correct (verified)

- `ExecRunner` is the production runner: it "shells out to a command (e.g. the
  `claude` CLI) ... with the prompt written to stdin," runs it in the request's
  `WorkingDir`, and substitutes `%MODEL%`/`%MAXTURNS%`/`%WORKDIR%` tokens in args
  (verified: `mlx-go-sia/runner.go:37-43`). "The Go port has no model-client
  dependency" — by design.
- `claude` (network) and a **local `mlx-go-lm` model** are then just two different
  commands behind the same runner. No `ClaudeCLIBackend`, no `MLXBackend`, no
  in-process tool loop to write or debug.
- `mlx-lm-generate` and `mlx-lm-chat` are **already built and on PATH**
  (`/Users/tmc/go/bin/`, verified) — the offline backend needs no build step.

## The minimal offline path (the whole of P2)

1. **Primary engine (online, pre-recorded for safety):** `ExecRunner` →
   `claude`. Already supported; this is the reference's intended production path.
2. **Offline proof:** a small wrapper script `pi-mlx` that reads the SIA prompt
   from **stdin**, calls `mlx-lm-generate` with a fixed local model, and writes
   the model's output where the target contract expects it; point `ExecRunner` at
   `pi-mlx`. The loop then runs **100% offline** through `mlx-go-lm`.

```sh
# pi-mlx (sketch): SIA prompt on stdin -> local model via mlx-lm-generate.
#!/usr/bin/env bash
set -euo pipefail
prompt="$(cat)"                     # ExecRunner writes the prompt to stdin
mlx-lm-generate --model "${PI_MLX_MODEL:?}" --max-tokens "${PI_MLX_MAXTOK:-2048}" \
  --prompt "$prompt"               # exact flags TBD: confirm mlx-lm-generate --help
# (write/emit output per the target contract in $PWD == WorkingDir)
```

`ExecRunner` config: `Command: "pi-mlx"`, `Args: [...]` with `%WORKDIR%`/`%MODEL%`
tokens as needed. Confirm `mlx-lm-generate`'s flags and the exact target output
contract before wiring.

## Scope boundary (what is explicitly NOT built)

- ❌ in-process Go agent tool loop (`read_file`/`write_file`/`run_command`)
- ❌ `ClaudeCLIBackend` (no value over `ExecRunner` + `claude`)
- ❌ `MLXBackend` in-process model driver (weak-model tool-calling risk)

If a *genuinely agentic* local engine becomes worth it later, it is a post-demo
enhancement, not hackathon scope.

## Deliverables

1. `pi-mlx` wrapper script (stdin prompt → `mlx-lm-generate` → target output).
2. `ExecRunner` configuration for both engines (`claude` online; `pi-mlx`
   offline), documented so the demo can switch with one flag.
3. A one-command offline smoke run of the SIA loop proving no network is used.

## Open questions for the NLM design review

- Does the chosen task's target-output contract fit a *single* `mlx-lm-generate`
  call, or does it need multi-turn (which a non-agentic wrapper can't do)? If
  multi-turn is required, is `mlx-lm-chat` enough, or does the offline claim need
  a small loop after all?
- Which local model (size/quant) is both *capable enough* for the demo task and
  *fast enough* to keep the loop watchable live?
- Is the offline proof a live demo segment, or a recorded one to save stage time?
